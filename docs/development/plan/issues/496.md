# Issue #496：本地路径 clone 停住（Fetching objects 0% CPU）修复计划（2026-09-24）

> 状态：设计计划（草稿）；全部任务卡 `pending`，尚未进行 Codex review。

## 文档职责

本计划解决 issue #496：对本地路径的大型仓库（实测 3,200 提交线性历史）执行 `libra clone <local-path>` 时，卡在 “Fetching objects” 阶段，CPU 0%，全部线程等待（2026-09-15 在 libra 0.22.31 复现，于 `issues/486.md` 作为 ER-AB-02 的例外另行报告）。目标是消除本地路径 clone 的挂起，使其以合理时间完成，并能对 `status --short --branch` 等后续命令正常工作。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- `libra clone <local-path>`（本地路径源，非 URL）的打包/拉取路径，尤其是大仓库（数千提交）下的性能与并发行为。
- “Fetching objects” 进度阶段：对象编码/传输/接收的等待位置与线程挂起原因。
- 与既有 pack 编码器（`pack_writer::encode_pack_bytes`）的复用（#487 已复用的先例）。
- 相关同步：`COMPATIBILITY.md`、clone 文档、`../libra-backend` 网站文档、clone 性能回归测试。

### 非目标

- URL 远端（http/ssh）clone（#480）。
- 浅克隆 `--depth`、bundle 源、`--bare`/`--mirror`（由 #474 承接；本计划只处理「本地路径直接 clone」的挂起）。
- 网络层长连接/凭证（#480）。
- 存储格式变更。

### 成功定义

- `libra clone <local-path>`（本地路径、约 3,200 提交）在合理时间内完成，不再出现 “Fetching objects” 0% CPU 挂起。
- clone 后 `status --short --branch`、`log --oneline` 正常，`[ahead N]`/`[behind N]` 语义正确。
- 大仓库 clone 挂起不再复现（用 #486 的 R1 fixture 或等价 fixture 做回归守卫，带合理超时预算）。
- 任务卡各自取得 C 组发布与 D 组证据，收口门全绿后才标记完成。

### 当前缺口

- 本地路径源是否走了与 URL 相同的“远端获取”路径，从而在无远端句柄时无限等待；
- “Fetching objects” 进度的对象枚举/编码是否存在 O(n²) 或死锁（如等待子进程/线程未信号）。
- 是否复用了 #487 已修复的 pack 编码器。
