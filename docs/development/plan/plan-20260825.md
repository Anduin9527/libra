# `libra code` provider 解析与凭据文案收口计划（2026-08-25）

> 模板版本: v2.1（按 [`plan-template.md`](plan-template.md) 成稿；本计划为新建计划，整份符合 v2.1）
> 触发: 用户报告 `libra code` 无参启动直接 `fatal: GEMINI_API_KEY is not set; export GEMINI_API_KEY or store it with ...` —— 且提示中给出的 `libra config --global add vault.env.GEMINI_API_KEY <value>` 实测不可执行（`config` 无 `add` 子命令，报 `LBR-CLI-002`）
> 用户裁决: **不考虑存量兼容**（2026-08-24 明确指示），破坏性行为变更以 `minor` 承载
> 文案口径: 全部用户可见文案统一采用 **ADR-PS-03「a 模式」**

## 文档职责

本文解决 `libra code` 的 provider 选择与凭据缺失反馈问题，目标是：**无参启动要么成功并说明用了谁，要么给出可直接复制执行的下一步**，并消除「生效 provider 与 UI/计费标签分裂」这一既有缺陷。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- `src/command/code.rs` 的 `--provider` 参数面、入口解析与写回。
- `src/internal/config.rs` 的凭据定位（新增「命中层」信息），以及新配置键 `code.defaultProvider`。
- `libra code` 三类用户可见文案：零凭据、唯一凭据、多凭据。
- 生效 provider 的单一事实源收口（banner / runtime kind / plan-mode / system preamble / usage 计费标签）。
- 会话元数据持久化 provider/model 与 `--resume` 继承。
- `docs/commands/code.md` EN + zh 的凭据优先级订正与新行为文档化。

### 非目标

- 不改 `src/internal/ai/providers/factory.rs` 的任何 provider 构造语义（只消费其 `MissingApiKey { env_var }`）。
- 不新增 provider、不改各 provider 的默认模型常量、不动 `--agent` profile 的绑定语义。
- 不做交互式 provider 选择器（TUI/提示符选单）；本计划只做非交互的判定与文案。
- 不新增 `StableErrorCode`（ADR-PS-04）。
- 不改 `--stdio`（MCP legacy）与 `--control stdio`（client shim）的能力面，只保证它们在零凭据下仍可启动。
- 不实现 provider 健康探活（网络握手 / key 有效性校验）——本计划只判断「是否已配置」。

### 成功定义

- 无参 `libra code` 在恰好配置一个凭据时直接启动，并在 stderr 说明选了谁、凭据来自哪一层。
- 零凭据时的报错含**可直接复制执行**的 `libra config set --global …`，以及免凭据的 `--provider codex` / 本地 ollama 路径。
- 多凭据时报可判定的歧义错误，列出全部候选（provider + 变量名 + 命中层），且**不含任何 key 值或片段**。
- 显式 `--provider` 时探测完全不介入；`--stdio` / `--control stdio` 在零凭据下仍可启动。
- `libra code` 打印的 provider、system preamble、usage 记录与实际驱动会话的 provider 完全一致（含 `--agent` 覆盖路径）。
- `--resume` 能从会话元数据继承 provider/model；显式冲突时告警而非静默换模型。
- 所有非延后任务 `Lifecycle=done` 且 `Acceptance=complete`；计划完成门全绿。

## 已决议设计决策

### ADR-PS-01: 取消 `--provider` 默认值，但不设为必填

- **Status:** Accepted
- **Context:** `default_value_t = Gemini` 使「显式指定」与「落到默认」不可区分（`src/command/code.rs:4446` 已因此误判），且让首次使用者撞上与自己配置无关的 `GEMINI_API_KEY`。用户已明确指示**不考虑存量兼容**。
- **Decision:** `provider: Option<CodeProvider>`，既不设默认值也不设 `required`。未指定时按 ADR-PS-05 的优先级链解析；解析不出唯一结果时报错而非猜测。
- **Alternatives considered:**
  - `required = true`：会让 `--stdio`（`src/command/code.rs:4446` 明确拒绝 `--provider`）无法调用、让 `--control stdio` 这个不构造 provider 的纯客户端被迫传值、与 `--agent` binding 重复指定，且唯一凭据场景仍要手打。
  - 保留 gemini 默认 + 仅改文案：`--stdio` 的显式性判断仍然是错的，GAP-02/GAP-03 不解决。
- **Consequences:** 无参 `libra code` 在多凭据时由「静默用 gemini」变为「报歧义错误」，属破坏性变更，由 PS-02 的 `minor` 承载。
- **Revisit when:** 出现交互式选择器需求（本计划非目标）。

### ADR-PS-02: provider 能力表是单一事实源；codex / ollama 不参与自动选择

- **Status:** Accepted
- **Context:** provider 事实目前散在 `src/command/code.rs:1741`（id 映射）、`src/command/code.rs:1766`（默认模型）、`src/command/code.rs:1808`（env 变量）、`src/command/code.rs:4282`（标志门）四处 match。而「有 key」不等于「可用」：`ollama` 仅在 base URL 指向 Cloud 时需要 key（`src/internal/ai/providers/factory.rs:297`）且缺 `--model` 会二段失败（`src/command/code.rs:1774`）；`codex` 根本没有 key 信号。
- **Decision:** 引入 `ProviderSpec { provider, id, api_key_env, key_required, needs_explicit_model, auto_selectable }` 表，作为 env 变量映射与文案枚举的唯一来源。**自动选择候选集 = `key_required && 凭据已配置`**（gemini/openai/anthropic/deepseek/kimi/zhipu 六个）；`codex` 与 `ollama` 的 `auto_selectable=false`，但必须出现在零候选文案的「免凭据路径」块。
- **Alternatives considered:** 直接对 8 个 provider 扫 env 变量——会把 `OLLAMA_API_KEY` 选成唯一候选后立刻死在 `--model is required`，也会让本地 ollama 用户被告知「你没有任何凭据」。
- **Consequences:** 新增 provider 时只需加表行；`needs_explicit_model` 与既有 `cli_default_model` 的错误分支必须保持一致（PS-01 AC）。
- **Revisit when:** 出现「key 可选但可自动选」的新 provider 形态。

### ADR-PS-03: 用户可见文案统一采用「a 模式」

- **Status:** Accepted（用户指令，2026-08-24）
- **Context:** 现有文案把结论与命令挤在一行，且命令本身不可执行（GAP-01）。
- **Decision:** 本计划新增或修改的全部用户可见诊断文案采用如下结构：

  ```
  <fatal|error>: <一句话结论，不含命令>

  Checked in order: <凭据查找链>          # 仅当结论与查找链有关时出现

  <推荐动作标题>:
      <可直接复制执行的命令>              # <可选注释>
      <可直接复制执行的命令>

  <备选动作标题>:
      <可直接复制执行的命令>
  ```

  强制规则：① 首行只给结论；② 命令块四空格缩进、一行一条、可原样粘贴执行；③ 推荐动作在前、备选在后；④ 任何情况下不输出 key 值、前缀或长度；⑤ 全部走 stderr，`--json` / `--machine` 下改为结构化字段而非自由文本。
- **Alternatives considered:** 保持单行紧凑文案——正是当前不可执行提示的成因。
- **Consequences:** PS-01/PS-02 的三类文案与 PS-05 的告警都按此结构；结构变化需修订本 ADR。
- **Revisit when:** CLI 全局采用统一的诊断渲染器。

### ADR-PS-04: 不新增 `StableErrorCode`

- **Status:** Accepted
- **Context:** 三类结局中有两类是错误：零候选（凭据缺失）与多候选（参数歧义）。
- **Decision:** 零候选复用 `LBR-AUTH-001`（`CliError::auth`，exit 128）；多候选与 `--model` 无 `--provider` 复用 `LBR-CLI-002`（`CliError::command_usage`，exit 129）。不新增变体，因此不触发 `compat_error_codes_doc_sync` 的新增行要求。
- **Alternatives considered:** 新增 `LBR-CLI-004 ambiguous-configuration`——语义与既有「参数无效或缺失」重叠，且要付一次错误码目录扩张成本。
- **Consequences:** 自动化只能靠退出码 + 文案区分两类错误；若将来需要机器可判定的歧义信号，改由 `--json` 结构化字段承载。
- **Revisit when:** 出现必须区分「歧义」与「参数非法」的自动化消费方。

### ADR-PS-05: 解析发生在 `execute()` 入口并写回 `args.provider`

- **Status:** Accepted
- **Context:** `args.provider` 在模型工厂之前就已被消费：plan-mode 默认（`src/command/code.rs:682`）、web 运行时分派（`src/command/code.rs:1207`）、banner（`src/command/code.rs:1272`）、provider match（`src/command/code.rs:2961`）、preamble（`src/command/code.rs:2824`）、usage 标签（`src/command/code.rs:2732` 与 `src/command/code.rs:2845`）、标志兼容门（`src/command/code.rs:4282-4345`）。现有 `--agent` 覆盖写在工厂内部（`src/command/code.rs:1741`），已造成标签分裂（GAP-04）。
- **Decision:** 解析在 `execute()`（按值持有 `CodeArgs`）中于 `resolve_code_preflight_working_dir` 之后、`validate_mode_args` 之前完成，并把结果写回 `args.provider`。`--stdio` 与 `--control stdio` 不进入解析（保持 `None`）。优先级：`--provider` → `--agent` binding → `--resume` 会话元数据 → 配置 `code.defaultProvider` → 自动探测。
- **Alternatives considered:** 在 `build_any_completion_model_for_args` 内部选择——永远到不了 codex 托管运行时（`src/command/code.rs:1207` 与 `src/command/code.rs:2961` 早已分派），且会把 GAP-04 的分裂面放大。
- **Consequences:** `load_code_env_file` 需从 `src/command/code.rs:1184`（`execute_web_only` 内）上提到 `src/command/code.rs:726`（`execute`）并向下传递。
- **Revisit when:** `execute()` 的模式分派被重构。
